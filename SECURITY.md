# Безопасность

Как в этом стеке ограничен ущерб от возможной компрометации контейнера.
Безопасность здесь — не «защищён или нет», а слои: каждый уменьшает вероятность
пробоя или урон от него.

---

## Что сделано

### Не под root

Приличные образы уже работают под непривилегированным пользователем — проверено:

| Сервис | UID |
|---|---|
| grafana | 472 |
| prometheus | 65534 (nobody) |
| loki | 10001 |
| node-exporter | 65534 |
| promtail | root + группа adm |
| nginx | master root, воркеры под nginx |
| cadvisor | root (обосновано ниже) |

nginx под root только у мастер-процесса — он слушает порты и переключает воркеры
на пользователя `nginx`. Запросы обрабатываются не под root.

### Урезанные capabilities

Docker по умолчанию оставляет контейнеру ~14 возможностей из 40. Всем сервисам,
кроме cadvisor, задан `cap_drop: [ALL]`, нужные возвращены по одной — по цепочке
ошибок при запуске:

| Сервис | Возвращено | Зачем |
|---|---|---|
| prometheus, grafana, loki, node-exporter | ничего | только читают, считают, отдают по HTTP |
| nginx | NET_BIND_SERVICE, SETUID, SETGID, CHOWN | слушать порты <1024, запустить воркеры, подготовить кэш |
| promtail | группа adm (не capability) | читать закрытые системные логи по праву группы |

Урезание не одинаково для всех: nginx потребовал четыре возможности, promtail —
доступ к защищённым файлам, остальные не потребовали ничего. Один флаг, разные
реакции — потому что сервисы делают разное.

### Read-only корень

`read_only: true` у всех сервисов, кроме cadvisor. Запись разрешена только
в тома (данные) и tmpfs (кэш, временное). Атакующий, попавший внутрь, не может
изменить файлы контейнера и закрепиться.

nginx пишет в tmpfs: `/var/cache/nginx`, `/var/run`, `/tmp`.

### no-new-privileges

`security_opt: [no-new-privileges:true]` везде. Запрещает процессу повысить
привилегии через setuid-бинарники внутри контейнера — перекрывает путь эскалации,
если атакующий уже выполнил код внутри.

### Сокет Docker не монтируется

cadvisor часто запускают с `/var/run`, через который внутрь попадает
`docker.sock` — а это доступ уровня root на хосте: через сокет создаётся
контейнер с примонтированным корнем системы, и флаг `:ro` не спасает (он
запрещает менять файл сокета, но не команды через него).

Проверено, что cadvisor берёт имена контейнеров из `/var/lib/docker/` (только
чтение) и без сокета работает полноценно — метрики по каждому контейнеру
с именами на месте. Монтирование `/var/run` убрано. Главная точка эскалации
закрыта.

### Сеть

Наружу опубликован единственный сервис — nginx с TLS. Grafana за ним порт
не публикует. Prometheus и Loki слушают только `127.0.0.1` — из локальной сети
недоступны, доступ через SSH-туннель. node-exporter, cadvisor, promtail не
публикуются вовсе, к ним обращаются только изнутри сети Docker.

### Ресурсы

Лимиты памяти у всех сервисов (`deploy.resources.limits`) — утечка в одном
контейнере не исчерпает память хоста. Ротация логов Docker настроена
(`max-size: 10m`, `max-file: 3`).

## Осознанные исключения

### cadvisor — привилегированный

`privileged: true` необходим: доступ к cgroups всех контейнеров и к `/dev/kmsg`.
Флаг отменяет механизм capabilities целиком, поэтому `cap_drop` к нему
не применяется. Это единственный привилегированный сервис, и сокет Docker
у него убран (см. выше) — то есть привилегии есть, но главная дыра закрыта.

Ужесточить можно, заменив `privileged` на точный список capability и монтирований
устройств, но список большой, хрупкий и по-разному ведёт себя на разных ядрах.
Для стенда не оправдано.

### Ключ сертификата — 644

На стенде ключ nginx читается всеми (`chmod 644`), потому что при `cap_drop: ALL`
мастер-процесс потерял `DAC_OVERRIDE` и не может прочитать файл, принадлежащий
другому UID. Для боевого сервера ключ кладут владельцем под UID мастера nginx
и оставляют 600.

### Секреты в .env, а не docker secret

Пробовал вынести пароль Grafana в `docker secret` через файл. В обычном compose
(не Swarm) это конфликтует с урезанными привилегиями: entrypoint Grafana читает
секрет на раннем этапе, и связка `cap_drop: ALL` + `read_only` + непривилегированный
пользователь даёт `permission denied`. Плюс сам файл секрета всё равно лежит
на диске открытым текстом — настоящего шифрования compose не даёт, только Swarm
или внешний Vault.

Оставлен пароль в `.env` как более честный для этого масштаба вариант.
Ограничения `.env`: значение видно в `docker inspect` и в `ps` на хосте.

## Уязвимости образов

Сканирование trivy показывает десятки HIGH/CRITICAL даже в официальных образах.
Это нормально:

- уязвимости в основном в транзитивных зависимостях (Go stdlib, OpenSSL, gRPC),
  а не в самом приложении;
- CRITICAL в отчёте не значит эксплуатируемый в конкретном сценарии
  (пример: «heap overflow на 32-битных системах» на 64-битном хосте не стреляет);
- часть со статусом `fixed` закрывается обновлением базового образа.

**Версия образа фиксирует и его уязвимости.** Тег `nginx:1.27-alpine` замораживает
версии внутренних пакетов на момент сборки. Поэтому образы периодически
пересобирают: `docker pull` под тем же тегом может подтянуть свежую сборку
с обновлёнными библиотеками.

Что делают на практике: обновляют базовые образы, берут alpine/slim/distroless
(меньше пакетов — меньше поверхность), оценивают остальное по эксплуатируемости,
сканируют регулярно.

```bash
# сканировать один образ
docker run --rm aquasec/trivy image --severity HIGH,CRITICAL nginx:1.27-alpine

# наглядно, зачем alpine
docker run --rm aquasec/trivy image -q --severity HIGH,CRITICAL nginx:1.27 | grep Total
docker run --rm aquasec/trivy image -q --severity HIGH,CRITICAL nginx:1.27-alpine | grep Total
```

## Принцип

Ни один слой не идеален. Вместе они делают так, что одна уязвимость не
превращается в захват сервера — defense in depth:

```
свежий образ       →  меньше известных дыр
минимальная база   →  меньше поверхность атаки
не под root        →  нет прав root для начала
cap_drop ALL       →  опасные способности отобраны
read_only          →  нельзя изменить файлы и закрепиться
no-new-privileges  →  нельзя повысить права трюком
сеть в loopback    →  меньше точек входа
без docker.sock    →  нет прямого пути к root на хосте
лимиты ресурсов    →  утечка не валит хост
```

Задача не сделать контейнер неуязвимым, а сделать так, чтобы взлом одного
контейнера не стал взломом всего сервера.

## Проверка

```bash
# кто под каким пользователем
for c in prometheus grafana loki node-exporter promtail cadvisor nginx; do
  PID=$(docker inspect -f '{{.State.Pid}}' monitoring-$c-1)
  echo -n "$c: "; ps -o user= -p $PID
done

# что применилось
for c in prometheus grafana loki node-exporter promtail nginx; do
  echo -n "$c: "
  docker inspect monitoring-$c-1 -f 'ro={{.HostConfig.ReadonlyRootfs}} drop={{.HostConfig.CapDrop}} sec={{.HostConfig.SecurityOpt}}'
done

# сокет недоступен cadvisor
docker exec monitoring-cadvisor-1 ls /var/run/docker.sock 2>/dev/null && echo "СОКЕТ ВИДЕН — плохо" || echo "сокета нет — хорошо"

# служебные порты только в loopback
ss -tlnp | grep -E '9090|3100'          # должно быть 127.0.0.1
```

## Чек-лист для нового сервиса

- [ ] не под root (`user:` или образ так собран)
- [ ] `cap_drop: [ALL]`, нужное вернуть по одной через `cap_add`
- [ ] `security_opt: [no-new-privileges:true]`
- [ ] `read_only: true`, запись в tmpfs и тома
- [ ] конфиги монтировать `:ro`
- [ ] наружу только через reverse proxy, служебное в loopback
- [ ] секреты не в образ и не в ENV, где возможно
- [ ] версия образа зафиксирована, база минимальная
- [ ] лимиты ресурсов заданы
- [ ] сокет Docker не монтировать без крайней нужды
- [ ] прогнать trivy
