# Дашборды

Четыре дашборда, 36 панелей. Разворачиваются через provisioning из этого
каталога — провайдер описан в `../provisioning/dashboards/dashboards.yml`.

JSON не поддерживает комментарии, поэтому описание панелей и запросов вынесено
сюда.

---

## Как это работает

Каталог монтируется в контейнер Grafana:

```yaml
- ./grafana/dashboards:/etc/grafana/dashboards:ro
```

Провайдер перечитывает файлы каждые 30 секунд (`updateIntervalSeconds: 30`),
поэтому после правки JSON перезапускать контейнер не нужно — достаточно обновить
страницу.

`allowUiUpdates: false` запрещает править дашборды через интерфейс: единственный
источник правды — файл в Git. Изменения, сделанные в UI, живут в базе Grafana
внутри тома и теряются при пересоздании.

**Проверка после правки:**

```bash
python3 -c "import json;json.load(open('dashboard-host.json'))" && echo "JSON валиден"
docker compose logs grafana --tail 20 | grep -i dashboard
curl -s -u admin localhost:3000/api/search?query= | python3 -m json.tool | grep '"title"'
```

Успешный провижининг четырёх дашбордов занимает около 50 миллисекунд. Если
в логах разница между `starting` и `finished` порядка микросекунд — файлы
не найдены, проверить монтирование и путь в провайдере.

**Дашборды написаны вручную, а не импортированы с grafana.com.** У готовых
источник данных задан переменной `${DS_PROMETHEUS}`, которая подставляется
только при импорте через интерфейс. При файловом провижининге она остаётся
как есть, и панели оказываются пустыми. Здесь `uid` источников прописан явно:
`prometheus` и `loki`, они заданы в `../provisioning/datasources/datasources.yml`.

## dashboard-host.json — «Хост»

Метрики машины. Источник — node-exporter, читает `/proc` и `/sys` хоста.

| №  | Панель                         | Запрос                                                                 | Смысл                                                                                  |
|----|--------------------------------|------------------------------------------------------------------------|----------------------------------------------------------------------------------------|
| 1  | Аптайм хоста                   | `node_time_seconds - node_boot_time_seconds`                           | Неожиданный сброс означает незамеченную перезагрузку                                   |
| 2  | Свободно на диске /            | `node_filesystem_avail_bytes / node_filesystem_size_bytes * 100`       | Основная причина отказов сервера. Пороги: красный до 20%, жёлтый до 40%                |
| 3  | Свободно inode /               | `node_filesystem_files_free / node_filesystem_files * 100`             | Кончаются независимо от места и валят запись при формально свободном диске             |
| 4  | Расхождение часов              | `abs(node_timex_offset_seconds)`                                       | Ломает аутентификацию, TLS и корреляцию логов. Порог 0.5 с                             |
| 5  | Загрузка процессора по режимам | `avg by(mode) (rate(node_cpu_seconds_total{mode!="idle"}[5m])) * 100`  | Разделение на user/system/iowait показывает, упирается система в вычисления или в диск |
| 6  | Load average                   | `node_load1`, `node_load5`, `node_load15` + число ядер                 | Очередь задач. Выше числа ядер — задачи ждут                                           |
| 7  | Память                         | total, занято, кэш и буферы, доступно                                  | Без разбивки картина врёт: кэш выглядит как занятая память                             |
| 8  | Использование swap             | `(SwapTotal - SwapFree) / SwapTotal * 100`                             | Активный своп означает, что памяти уже не хватает                                      |
| 9  | Дисковый ввод-вывод            | `rate(node_disk_read_bytes_total[5m])`, `written`                      | Фильтр `device!~"loop.*"` убирает петлевые устройства snap                             |
| 10 | Время ожидания диска           | `avg(rate(node_cpu_seconds_total{mode="iowait"}[5m])) * 100`           | Выше 20% — диск стал узким местом                                                      |
| 11 | Сетевой трафик                 | `rate(node_network_receive_bytes_total{device!="lo"}[5m])`, `transmit` | Фильтр убирает loopback                                                                |

**Про `rate([5m])`** — счётчики node-exporter монотонно растут с момента запуска.
`rate` считает прирост в секунду за скользящее окно пяти минут, поэтому графики
показывают скорость, а не накопленное значение.

**Панель 6** намеренно включает четвёртый ряд — число ядер:
`count(count(node_cpu_seconds_total) by (cpu))`. Без него load average не с чем
сравнивать: значение 2 на двух ядрах и на шестнадцати означает разное.

## dashboard-containers.json — «Контейнеры»

Метрики отдельных контейнеров. Источник — cadvisor, читает cgroups.

**Без cadvisor эти панели пусты.** node-exporter рассказывает про хост целиком
и отдельные контейнеры не видит.

| № | Панель | Запрос | Смысл |
|---|---|---|---|
| 1 | Контейнеров запущено | `count(count by(name) (container_last_seen{name!=""}))` | Двойной `count` обязателен: метрика приходит несколькими сериями на контейнер, без агрегации число завышается вдвое |
| 2 | Максимум от лимита памяти | `max(usage / spec_limit * 100)` | Худший контейнер. Пороги: жёлтый с 70%, красный с 85% |
| 3 | Перезапусков за час | `sum(changes(container_start_time_seconds[1h]))` | Ненулевое значение означает, что кто-то падал |
| 4 | Память контейнеров | `container_memory_usage_bytes{name!=""}` | Потребление по каждому |
| 5 | Процессор контейнеров | `rate(container_cpu_usage_seconds_total[5m]) * 100` | 100% = одно ядро целиком |
| 6 | Приближение к лимиту памяти | `usage / spec_limit * 100` | Предупреждает до OOM, а не после. Работает только при заданных лимитах |
| 7 | Перезапуски контейнеров | `max by(name) (changes(container_start_time_seconds[1h]))` | `max by(name)` схлопывает серии старых и новых экземпляров одного контейнера |
| 8 | Сеть контейнеров | `rate(container_network_receive_bytes_total[5m])`, `transmit` | Две серии на контейнер: приём и передача |

**Фильтр `{name!=""}` обязателен во всех запросах.** Без него в выборку попадает
корневая cgroup с `id="/"` — метрики всей системы вперемешку с контейнерными.

**Про лишние ряды в легенде.** За выбранный период в неё попадают все экземпляры
контейнеров, включая пересозданные — у них разный `id` в метках, и Grafana считает
их разными рядами. Сузи диапазон времени либо используй `max by(name)`, как
в панели 7.

## dashboard-stack.json — «Здоровье стека»

Мониторинг самого мониторинга. Источники — метрики Prometheus, Loki и запрос
к Loki через LogQL.

| № | Панель | Запрос | Смысл |
|---|---|---|---|
| 1 | Доступность целей | `sum(up) / count(up) * 100` | Меньше 100% означает, что кто-то не отвечает. Пороги: зелёный только на 100% |
| 2 | Размер базы Prometheus | `prometheus_tsdb_storage_blocks_bytes` | Контроль ретенции: растёт ли база и работает ли ограничение в 2 ГБ |
| 3 | Рядов метрик в памяти | `prometheus_tsdb_head_series` | Ряд = уникальная комбинация имени метрики и меток. Рост без новых целей означает взрыв кардинальности |
| 4 | Состояние целей | `up` | По одной линии на цель, 1 или 0. Видно, кто и когда отваливался |
| 5 | Длительность сбора метрик | `scrape_duration_seconds` | При `scrape_timeout: 10s` цель помечается недоступной, если не уложилась. График показывает запас |
| 6 | Скорость приёма логов в Loki | `sum(rate(loki_distributor_lines_received_total[5m]))` | Падение в ноль означает, что логи перестали поступать |
| 7 | Скорость записи метрик | `rate(prometheus_tsdb_head_samples_appended_total[5m])` | Отсчёт = одна точка одного ряда. При 9000 рядов и интервале 15 с выходит около 280 в секунду |
| 8 | Поток логов по сервисам | `sum by(compose_service) (rate({compose_project="monitoring"}[5m]))` | Единственная панель этого дашборда с источником Loki. Показывает, кто именно пишет |

**Панель 7 при правке.** Метрика приходит двумя сериями: `type="float"`
(обычные отсчёты) и `type="histogram"` (нативные гистограммы, у нас ноль).
В правилах оповещения это давало ложное срабатывание, там запрос обёрнут в `sum`.
На панели разделение наглядно и оставлено как есть.

**Панели 2 и 3 — пороги задавать обязательно.** Без них Grafana применяет
умолчания (красный выше 80), и панель с 9000 рядов всегда красная без всякого
смысла.

## dashboard-logs.json — «Логи»

Девять панелей типа `logs`, все запросы на LogQL к Loki.

| № | Панель | Запрос | Смысл |
|---|---|---|---|
| 1 | Неудачные попытки входа по SSH | `{job="varlogs"} \|~ "Failed password\|Invalid user\|authentication failure"` | Подбор пароля виден сразу |
| 2 | Успешные входы по SSH | `{job="varlogs"} \|~ "Accepted password\|Accepted publickey"` | Кто и откуда зашёл — нужно при разборе инцидентов |
| 3 | Использование sudo | `{job="varlogs"} \|~ "sudo:"` | Кто повышал права и для чего |
| 4 | Блокировки ufw | `{job="varlogs"} \|~ "UFW BLOCK"` | Сканирование портов и попытки достучаться до закрытых сервисов |
| 5 | Ошибки ядра | `{job="varlogs", filename="/var/log/kern.log"} \|~ "(?i)(error\|fail\|warn)"` | Проблемы с диском, памятью, сетевой картой |
| 6 | Убийства по OOM | `{job="varlogs"} \|~ "Out of memory\|Killed process\|oom_kill"` | Ядро отстреливает процессы |
| 7 | Ошибки контейнеров стека | `{compose_project="monitoring"} \|~ "(?i)(error\|fatal\|panic)"` | Единая лента проблем по всем сервисам |
| 8 | Установка и удаление пакетов | `{job="varlogs", filename="/var/log/dpkg.log"}` | Кто менял состав системы и когда |
| 9 | События сети Docker | `{job="varlogs"} \|~ "docker0: port\|veth"` | Жизненный цикл veth при старте и остановке контейнеров |

**Синтаксис LogQL.** Селектор в фигурных скобках выбирает потоки по меткам,
оператор `|~` фильтрует строки регулярным выражением. `(?i)` делает выражение
нечувствительным к регистру.

**Два источника логов, две группы меток:**

```
{job="varlogs"}              системные логи хоста через promtail
{compose_project="..."}      логи контейнеров через драйвер Loki
{compose_service="..."}      конкретный сервис стека
```

Панели 1–6, 8, 9 работают с системными логами, панель 7 — с контейнерными.

**Логи самих Loki и promtail сюда не попадают.** Оба исключены из драйвера
логирования и пишут в `json-file` — смотреть через `docker compose logs`.
Причина в README проекта, раздел про круговую зависимость.

## Типовые проблемы

**Панель пуста.** Проверь, существует ли метрика:

```bash
curl -sG 'localhost:9090/api/v1/query' --data-urlencode 'query=ИМЯ_МЕТРИКИ' | python3 -m json.tool
```

Пустой `result` означает, что данных нет. Причины: не запущен нужный экспортер,
метрика называется иначе в твоей версии, или запрос не возвращает серий из-за
несопоставимых меток.

Найти правильное имя:

```bash
curl -s localhost:9090/api/v1/label/__name__/values | python3 -m json.tool | grep -i КЛЮЧЕВОЕ_СЛОВО
```

**Панель логов пуста.** Проверь метки:

```bash
curl -s 'localhost:3100/loki/api/v1/labels' | python3 -m json.tool
curl -s 'localhost:3100/loki/api/v1/label/filename/values' | python3 -m json.tool
```

Если `filename` нет в списке, promtail не отправляет логи, и панели с фильтром
по имени файла работать не будут.

Отдельная особенность: **пустой результат Loki отдаёт как синтаксическую ошибку**
`parse error: unexpected IDENTIFIER`, хотя селектор корректен.

**Дашборд не появился.** Проверь монтирование и путь:

```bash
ls -la grafana/dashboards/
docker compose exec grafana ls -la /etc/grafana/dashboards/
cat grafana/provisioning/dashboards/dashboards.yml   # path должен совпадать
```

**Изменения не применяются.** Провайдер перечитывает файлы раз в 30 секунд.
Если ждать надоело — `docker compose up -d --force-recreate grafana`.

## Что можно доработать

- **Переменные дашборда** (`templating`) — выпадающий список для выбора
  контейнера или файловой системы вместо показа всех сразу.
- **Аннотации** — вертикальные линии на графиках в моменты деплоя или
  срабатывания алертов.
- **Ссылки между дашбордами** — переход с панели «Контейнеры» на логи
  конкретного сервиса с сохранением временного диапазона.
